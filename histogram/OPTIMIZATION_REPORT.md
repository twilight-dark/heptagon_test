# Histogram 多线程优化分析报告

## 1. 当前代码与任务边界

本报告基于当前仓库静态分析，先给出实现路线与验证计划，不修改算子实现，也不声称已取得性能收益。

| 文件 | 当前作用与状态 |
| --- | --- |
| `src/histogram.cpp` | 待实现函数 `std::vector<int> histogram(int N, int M, const std::vector<int>& in)`；函数体为空、缺少返回值，当前不能作为有效性能参照 |
| `baseline.cpp` / `baseline.h` | 串行基线：创建长度为 M 的零数组，逐元素执行 `++out[in[i]]`；M ≤ 0 时返回空数组 |
| `src/main.cpp` | 生成输入，执行基线与选手函数，比较输出并报告耗时和加速比 |
| `Makefile` | 默认使用 `-O3 -std=c++17 -march=native -fopenmp -pthread -Wall -Wextra` |

实现仅使用 OpenMP、C++ 标准库及自编算法，不引入现成高性能 Histogram 或其他并行计算库。优先采用 OpenMP，减少线程管理代码；没有必要同时叠加两套线程机制。

### 输入语义

- 正常输入约定：N ≥ 0、`in.size() ≥ N`，前 N 个元素均满足 `0 ≤ in[i] < M`；只统计前 N 个元素。
- 保持基线的 M ≤ 0 行为；M > 0 且 N = 0 时返回 M 个零。
- 当前代码没有为非法输入定义统一错误处理，后续应先明确接口契约，避免在计时热循环中无条件加入逐元素检查。
- 合法 N 的类型是 `int`，单桶计数不超过 N，因此 `int` 计数满足当前接口范围；地址偏移、内存大小和线程边界计算使用 `std::size_t` 或 64 位整数，避免中间乘法溢出。

### 2.1 用例分组

| `L2N_L1M` | 100,000 | 1,000 | 均匀 | 串行与并行的切换点 |

| `L2N_midM` | 1,000,000 | 20,000 | 均匀 | 每线程计数表的缓存占用 |
| `L3N_largeM` / `L3N_largeM_hot` | 10,000,000 | 1,000,000 | 均匀 / 热点 | 大表随机访问、清零和归并成本 |

| `DRAMN_largeM_single` | 100,000,000 | 1,000,000 | 全部为 0 | 极端集中分布、重复更新依赖 |

热点生成器约有 90% 的元素来自前 `max(1, M/100)` 个桶，剩余部分来自全范围；这不是“90% 都在同一个桶”。`Sequential` 分布已实现，但未纳入用例表。

### 2.2 现有计时规则

- 每个用例预热 1 轮，随后按 N 重复 10、5 或 3 轮，分别取基线与选手函数的最小耗时。
- 输入生成在计时之外；函数内部的分配、输出清零、私有表初始化与归并都在计时之内。返回结果赋给旧 `out` 的开销也在计时区间内。
- 总加速比为 `sum(base_ms) / sum(sub_ms)`，不是各用例加速比的算术平均；绝对耗时大的用例影响更大，但仍应检查每个小用例是否退化。
- 基线与选手使用独立输入副本，但每轮固定先基线后选手。这不能保证缓存、频率与调度状态完全对称；最小值也不能反映延迟稳定性。
- 正确性仅比较最后一轮的输出，可能遗漏偶发数据竞争；补充验证应检查每次调用。

### 2.3 本地环境与可迁移性

本次检查得到：AMD Ryzen 7 5800H，8 核 / 16 逻辑线程，L1d 合计 256 KiB、L2 合计 4 MiB、L3 16 MiB，GCC 13.3.0；环境报告 Microsoft hypervisor。可见内存约 6.7 GiB。

测试注释按 Xeon Gold 6338 的缓存规模设计，因此 `L2N`、`L3N` 等名字不能直接代表本机实际缓存驻留情况。线程数和阈值需本地测量，运行时还需关注可用 CPU、后台负载和虚拟化调度影响。`-march=native` 生成的程序也不宜直接拷贝到不同指令集的机器上使用。

## 3. 首选方案：私有直方图 + 分块归并

### 3.1 工作流程

1. 处理 M ≤ 0、N = 0、M = 1 等边界；小 N 使用串行路径。
2. 为每个工作线程建立独立、清零的 M 桶计数表。
3. 将输入按连续区间静态分配，各线程只更新自己的计数表。
4. 所有线程统计完成后同步，再按输出桶区间分工，将各私有表相加。
5. 返回长度为 M 的结果。

统计阶段不存在跨线程写同一个计数器，不需要逐元素原子操作。总工作量约为 `O(N + T×M)`，额外空间约为 `T×M×sizeof(int)`，其中 T 为实际参与线程数。并行收益必须足以覆盖线程调度、清零和归并的额外成本。

例如 M = 1,000,000 时，每线程计数表约 3.81 MiB；8 线程约 30.52 MiB，16 线程约 61.04 MiB，尚未包含输入与输出。该占用已超过本机 L3，不能假设“私有表一定驻留缓存”。

### 3.2 区间划分与余数处理

默认可用 `omp for schedule(static)` 自动覆盖所有元素。手动划分时，在并行区域内获取实际线程数 T 与线程编号 t，使用：

```cpp
const std::size_t n = static_cast<std::size_t>(N);
const std::size_t q = n / T;
const std::size_t r = n % T;
const std::size_t begin = t * q + std::min(t, r);
const std::size_t end = begin + q + (t < r ? 1 : 0);
// 处理 [begin, end)
```

其中 T、t 也用 `std::size_t`。前 r 个线程多处理一个元素，各区间无重叠、无遗漏；N < T 时允许空区间。不要只处理 `N/T` 个元素而丢掉尾部，也不要假定请求的线程数就是实际线程数。

统计任务每个元素的工作量接近，连续静态划分有利于顺序读取，通常不需要 dynamic 调度。候选线程数应受 N、私有表内存预算及实测结果共同约束。

### 3.3 数据布局、同步与归并

- 使用线程优先布局 `local[thread][bin]`，避免不同线程的同号桶相邻，造成伪共享。
- 私有行首及行跨度按缓存行对齐；本机可从 64 字节开始验证。仅把跨度取整还不够，分配基址也应对齐。
- 使用一次并行区域完成初始化、统计和归并；统计结束与读取他人私有表之间必须保留 barrier。
- 各线程自行初始化自己的私有表；如果容器构造已经串行清零，应避免再次无意义清零。若采用未初始化存储，必须保证每个被读计数器先被初始化。
- 归并按输出的连续块分配，每块由一个线程独占；块内依次读取各线程的连续计数段，减少跨大表的逐桶跳跃，并为编译器向量化创造条件。
- 小 M 的归并量很少，可在同步后由单线程归并，避免额外调度；大 M 采用并行分块。分块边界尽量按缓存行对齐。
- 每个输出元素只由一个线程写，不需要原子归并。绝不能用无同步的共享 `++out[in[i]]`。

## 4. 按规模与分布选择优化

### 4.1 N 较小：避免并行固定开销

小 N 优先串行计数，保持简单循环和顺序输入访问。阈值不应只看 N：M 很大时，输出初始化本身就可能主导耗时，多份私有表反而进一步放大成本。

建议扫描不同 N、M 组合，测得串行与私有表并行路径的交点，再决定切换条件。可用 `N/T` 表示每线程输入工作量、`T×M` 表示清零与归并规模，建立粗粒度策略，不在未测量前写死“某个 N 必须并行”。

### 4.2 M 较小：多路局部累加

- M = 1：在合法输入契约下，所有元素只能为 0，直接返回单元素结果 N，无须扫描输入。
- M = 4 等极小桶数：尝试固定大小计数表或少量标量计数器，消除动态分配并便于展开；不能假定编译器一定把动态下标数组放入寄存器。
- 每线程维护 K 份小表，按输入位置轮流更新，最后先合并线程内的 K 份表。可测试 K = 2、4、8，以打断连续更新同一地址的依赖链。
- 尾部不足 K 的元素必须单独处理；空间增长为 `T×K×M`，只在小 M 路径启用。

即使没有跨线程竞争，全相同输入上的单个私有计数器仍存在连续读改写依赖。因此多路累加既可用于并行路径，也值得在小 M 的串行路径上测试。

### 4.3 高竞争、热点与全相同输入

线程私有表首先消除跨线程竞争，但大表和局部依赖仍可能限制速度。可按优先级继续探索：

1. **局部热点计数。** 从少量样本提出热门值候选，在完整扫描中把匹配元素累加到独立计数器，其他元素进入常规私有表，结束后合并。候选值不准只影响速度，不影响正确性；均匀输入上的额外判断必须计入成本。
2. **连续重复段聚合。** 将连续相同值合成一次 `count += run_length`，尤其适合全相同或长重复段输入；随机热点未必有长连续段，不能等同处理。每线程独立统计其区间，即使重复段跨边界也可正确相加。
3. **局部全相同块快路径。** 验证一个块内全部等于候选值后，用块长度更新一次；验证失败则执行普通统计。必须计算失败回退造成的重复读取成本。

样本不能证明整个输入全相同，禁止只检查首元素或少量样本就设置 `out[value] = N`。同样，不能因为公开 Single 用例全为 0 就硬编码结果，也不能用输入地址或 N、M 缓存上一次输出。

### 4.4 M 较大：控制内存与归并开销

| 候选方式 | 适用条件 | 成本与限制 |
| --- | --- | --- |
| 减少私有表线程数 | T×M 较大，缓存与归并压力明显 | 可能降低输入并行度，需比较总耗时 |
| 私有表 + 已触及桶列表 | 实际访问桶很少 | 可减少归并遍历；若仍新建并清零整表，就没有消除初始化成本；标记或代数机制增加内存和复杂度 |
| 线程私有稀疏表 | M 远大于 N、不同值数量很少 | `std::unordered_map` 的哈希、分配与间接访问通常昂贵，只作为补充候选；最终仍必须创建 M 个输出桶 |
| 热点计数器 + 其余桶常规处理 | 大 M 且集中于少数值 | 样本及判断有成本，需保持任意输入下精确计数 |
| 按桶范围分区后分别计数 | 大 M 随机更新明显受缓存限制 | 增加分区、前缀和与临时输入缓冲，属于后续复杂方案 |

不建议直接让每个桶块重新扫描全部输入：若有 B 个桶块，会变成约 B×N 次输入检查。若推进分区方案，应先一次分区，再处理各分区，避免反复全量扫描。

### 4.5 均匀与集中分布的区别

- 均匀、小 M：优先小表私有化与多路累加；一般无需分布检测。
- 均匀、大 M：关注随机更新延迟、缓存容量、内存带宽与 T×M 开销；更多线程不一定更快。
- 热点分布：私有化后工作集可能较小，但仍需处理落在全范围的尾部元素，不能只分配热点区间。
- 全相同分布：重点减少重复读改写，可用多路累加、重复段或块聚合；除 M = 1 的契约特例外，仍需完整读取或验证输入。

分布自适应放在基础实现之后：先证明相对稳定的收益，再引入抽样和分支，避免检测成本吞掉收益。

## 5. 其他并行方案的取舍

| 方案 | 判断 |
| --- | --- |
| 每元素 OpenMP atomic | 实现简单、只需一份输出表；可作为对照或内存受限候选，但小 M / 热点下容易严重争用，即使均匀分布也有原子及缓存一致性成本 |
| 每元素 mutex / critical | 临界区过细、串行化明显，不作为主方案 |
| OpenMP 数组 reduction | 可作为简洁候选；实质仍涉及私有计数和归并，需要确认编译器支持、内存分配行为及大 M 表现 |
| `std::thread` | 可实现相同分块与私有化；每次调用创建、join 线程有成本，线程池又增加生命周期和同步复杂度，第一版优先 OpenMP |
| 对 `++hist[in[i]]` 强行 SIMD | 相同索引存在依赖，不能直接声称迭代独立；更适合先向量化清零、归并或固定桶比较等无冲突部分 |

OpenMP 路径可测试 `OMP_NUM_THREADS=1,2,4,8,16`、`OMP_DYNAMIC=FALSE`、`OMP_PLACES=cores` 以及 `OMP_PROC_BIND=close/spread`。记录实际线程数与绑定结果，不在算子内强行覆盖调用方的全局运行时配置。

## 6. 推荐实施顺序

| 阶段 | 具体工作 | 完成标准 |
| --- | --- | --- |
| P0：可运行版本 | 补齐与基线一致的串行实现和边界处理，建立正确性对照 | 现有 12 个用例通过，无缺失返回值等编译警告 |
| P1：主并行路径 | 连续静态分块、线程私有表、同步后分块归并；小 N 保留串行 | 余数与不同线程数验证通过；记录每个用例的完整调用耗时 |
| P2：小 M | M = 1 特例，极小 M 固定表，K 路累加及尾部处理 | 小 M 用例有可重复收益，边界与尾部无漏计 |
| P3：大 M | 私有表内存预算、线程数限制、归并块大小与布局调优 | 大 M 总耗时改善，记录峰值内存，不能只优化统计循环 |
| P4：集中分布 | 分别验证热点计数和重复段 / 块聚合，必要时增加抽样 | 集中输入加速，均匀输入的检测开销可接受 |
| P5：策略收敛 | 依据 N、M 与测量结果选路，删除无收益复杂分支 | 全部正确性测试通过，重复测量稳定，形成最终对比表 |

每阶段单独比较，优先保留机制清晰、收益稳定的版本。调优参数应包括线程数 T、小 N 切换点、局部副本数 K、归并块大小及私有表总内存上限；不必一次穷举所有组合。

## 7. 验证矩阵与性能记录

### 7.1 正确性补充

使用独立补充测试保留原始基准，逐桶与串行参考结果比较，并使用 64 位求和检查 `sum(out) == N`。

- 边界：M ≤ 0、N = 0、N = 1、M = 1、M > N，以及 `in.size() > N` 时只统计前 N 项。
- 线程划分：线程数 1、2、3、4、7、8、16；N 取 T−1、T、T+1、2T+1、1003 等，覆盖 N < T 和不能整除的情况。
- 分布：均匀、当前热点、全相同、顺序循环、两个值交替、长连续重复段，以及不同线程区间具有不同热点。
- 对抗快路径：全部为 M−1；仅首 / 尾 / 中间一项不同；样本区间相同而其他位置不同；M 不是副本数或块大小的倍数。
- 状态隔离：同一个输入 vector 修改内容后再次调用、不同 N/M 连续调用、重复执行同一用例，排查未清零和错误结果缓存。
- 用 AddressSanitizer / UndefinedBehaviorSanitizer 检查越界和未定义行为，诊断构建不用于性能结论；并行同步另外结合代码审查与反复压力测试验证。

### 7.2 性能实验

1. 实现可运行版本后执行 `make -C histogram`，保留现有基准输出；当前空函数不值得直接运行测速。
2. 固定线程配置，每次只修改一个主要因素；每个配置执行多次独立进程，记录原基准的最小值，也在补充基准记录中位数与波动。
3. 扫描小 N 切换区间，以及计数表跨本机缓存容量附近的 M；覆盖不同分布，不只针对公开 12 个用例调参。
4. 在补充基准中交换基线与选手调用顺序，明确预热、热数据与冷数据条件；不要把更改测试方法后的数字直接混入原始评分。
5. 用单独诊断版本拆分分配 / 清零、统计、归并耗时；小任务分段计时可能扰动结果，最终比较仍以完整调用为准。
6. 对大 N 检查读带宽与线程扩展曲线；输入约为 `4N` 字节，私有表清零和归并还会带来额外流量，不能把 `4N/耗时` 当作全部内存带宽。

建议记录字段：代码版本、编译参数、CPU / 线程绑定、用例 N/M/分布、实际 T、K、完整耗时最小值 / 中位数、各阶段诊断耗时、私有表大小、正确性及相对基线加速比。

## 8. 当前建议

先完成“串行回退 + 静态输入分块 + 私有直方图 + 分块归并”，再加入小 M 多路累加和大 M 线程数限制。热点检测、稀疏表与输入分区作为后续实测驱动的选项。当前没有运行有效的优化实现，具体阈值、线程数与加速倍数均待验证。
